# Capture ingestion

How an operator gets real captured media from a device into Chaya 02 safely. Verified end to end
against real PostgreSQL, MinIO, ClamAV and Keycloak (see "What is verified").

## Flow

```
create session -> [init media -> PUT parts... -> complete media] x N -> complete upload -> start processing
   CREATED          UPLOADING  (per file: PENDING -> VALIDATING -> ACCEPTED | REJECTED | QUARANTINED)
                                              UPLOADED -> VALIDATING -> READY_FOR_PROCESSING -> PROCESSING
```

Capture states: `CREATED, UPLOADING, UPLOADED, VALIDATING, READY_FOR_PROCESSING, PROCESSING, COMPLETED, FAILED`.
Allowed moves are forward-only along that line; any non-terminal state may go to `FAILED`; `COMPLETED` and
`FAILED` are terminal. Enforced by the API (`CaptureStatus`) and by a database trigger, which rejects anything
else even for direct SQL. `PROCESSING -> COMPLETED/FAILED` belongs to the job engine milestone: today
starting processing queues a real `MEDIA_FILTER` job that stays `QUEUED` until a worker claims it. The API
and UI say so; nothing pretends the pipeline ran.

## API (all under `/api/v1/venues/{venueId}/captures`, roles: admin, venue-manager, operator)

| Call | Purpose |
|---|---|
| `POST /` `{floorId?, device{}, startedAt?}` | Create a session. `device` is free-form JSON (max 16 KiB); operator, venue, org come from the token |
| `GET /`, `GET /{id}` | List / inspect (status, device, start, end, duration, quality state, media counts) |
| `POST /{id}/media` `{kind, filename, contentType, sizeBytes, sha256}` | Open an upload. Returns `mediaId`, `partSizeBytes`, `totalParts` |
| `PUT /{id}/media/{m}/parts/{n}` raw body, optional `X-Part-Sha256` | Send one part. Exactly `partSizeBytes` (last part: the remainder). Idempotent |
| `GET /{id}/media/{m}` | Status and which parts the server holds (resume) |
| `POST /{id}/media/{m}/complete` | Assemble and start asynchronous validation. Also retries a `QUARANTINED` file |
| `GET /{id}/media` | List capture artifacts with status, detected type, rejection reason |
| `POST /{id}/complete-upload` `{endedAt?, durationSeconds?}` | Finish the upload phase (see below) |
| `POST /{id}/processing`, `GET /{id}/processing` | Start processing / read status and job list |
| `GET/POST /api/v1/venues/{venueId}/floors` | Floors a capture can be recorded against |

Errors are problem+json with a stable `code` (`UNSUPPORTED_MEDIA_TYPE` 415, `FILE_TOO_LARGE` 413,
`CHECKSUM_MISMATCH` 422, `MISSING_PARTS`, `INVALID_CAPTURE_TRANSITION`, `UPLOADS_NOT_SETTLED`,
`INSUFFICIENT_MEDIA`, `STORAGE_INTEGRITY` 409, `STORAGE_UNAVAILABLE` 503 ...).

## Resumable chunked upload
Bytes go through the backend into MinIO as an S3 multipart upload (8 MiB parts, min 5 MiB). The backend stays in
the data path on purpose: nothing is trusted until the server has verified it. Each part is checked against
its exact expected length and optional `X-Part-Sha256`. Parts are recorded in `capture_media_part`; after a
dropped connection the client asks `GET .../media/{m}`, sends only the missing parts and completes. Part
uploads can be repeated safely. Limit: 10 000 parts per file.

## Upload security, in the order it happens
1. **At init (before any byte):** claimed MIME type (case/parameters normalised) must be in the allowlist for the declared kind; declared size within the per-kind limit; sha256 well-formed; file count within limit. Otherwise 415 / 413 / 400.
2. **Per part:** length exact (declared size cannot be exceeded), part checksum if supplied.
3. **Filename:** sanitised (directory part stripped for `/` and `\`, control characters and `..` removed, length-limited) and stored as metadata only. It is never part of an object key or path.
4. **Object key:** `org/{orgId}/venue/{venueId}/capture/{captureId}/raw/{mediaId}` - UUIDs only, generated by the server. No path traversal is possible.
5. **Asynchronous validation** (`MediaValidationService`), after `complete`:
   assemble -> stored size equals declared -> SHA-256 of the stored bytes equals declared -> **ClamAV scan** -> **real content type via Apache Tika** must equal the claim and be allowlisted -> metadata files must be a JSON object.
   Malware is scanned before anything is interpreted. A definite failure is `REJECTED` and the object is deleted. Anything that could not be checked (scanner or storage unreachable) is `QUARANTINED`: kept out of use, blocks completing the capture, and re-validated by calling `complete` again.
6. **Fail safe:** `CLAMAV_ENABLED=false`, an unreachable daemon, or a clamd error (for example a stream over its size limit) all yield `UNAVAILABLE`, i.e. quarantine. There is no code path that accepts an unscanned file.
7. **Restart safety:** files that were `VALIDATING` when the process stopped are validated again at startup.

Allowed types: video `mp4, quicktime, webm, x-matroska`; image `jpeg, png, heic`; metadata `application/json`.
Default limits (config `chaya.uploads.*`): video 4 GiB, image 50 MiB, metadata 1 MiB, 5000 files per capture.
ClamAV's stream limit defaults to 25 MB; Compose raises it to 4000M (clamd's maximum) so large videos can be scanned.

Known limits: ClamAV is signature-based (an EICAR string embedded inside a valid PNG is not flagged, only a
whole EICAR file is); clamd cannot scan files over 2 GiB, so larger videos are quarantined until a different
scan strategy exists; video is not decoded or checked for playability at ingestion.

## Completing a capture (`complete-upload`)
Requires status `UPLOADING`, every file settled (no pending/validating/quarantined), and at least one accepted
video or `min-images-without-video` (default 20) accepted images. Then `UPLOADED -> VALIDATING`, a real
integrity check that every accepted object still exists in storage with the recorded size, and
`READY_FOR_PROCESSING` (or `FAILED` with `STORAGE_INTEGRITY`). `endedAt`/`durationSeconds` are recorded; the
capture quality assessment stays `NOT_ASSESSED` until that pipeline exists.

## Data model (migration V9)
`capture_session` gained device metadata, duration, quality state, failure code/message and the lifecycle
trigger. `capture_media` holds one row per file (status, kind, sanitised name, claimed and detected type,
declared and verified SHA-256, object key, scan result, rejection code) with a trigger making terminal
states immutable and blocking deletes. `capture_media_part` tracks parts. The database never stores file bytes.
A capture yields at most one `scan`, created when processing starts.

## Web UI (`/capture`)
Sign in with Keycloak (authorization code + PKCE, tokens in memory) -> pick venue and optional floor ->
create session (this browser's real user agent/screen recorded as device metadata) -> choose files ->
per-file checksum and upload progress bars, validation verdicts with actionable messages, Resume /
Retry-validation buttons -> Finish upload -> Start processing -> job table polled every 3 s. There is no
coverage heat map yet. The page does not restore an in-progress session after a full reload.

## What is verified
- `mvn verify`: real PostgreSQL + real MinIO in Testcontainers, real files (PNG/JPEG via ImageIO, MP4-signature fixtures, JSON). The malware scanner is replaced by a stand-in only in those tests.
- The production clamd client against a fake daemon (protocol) and, on demand, a real ClamAV container (`ClamAvLiveTest`).
- The built jar run against real Postgres, MinIO, ClamAV and Keycloak with a script (token from Keycloak, 3-part video, EICAR, disguised executable, checksum, complete, processing).
- Not verified: the browser UI in an actual browser (lint, typecheck, unit tests and production build only).
